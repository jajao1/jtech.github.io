Middleman for .NET

Lightweight CQRS mediation without framework drag.

Middleman is an in-process mediator for .NET applications built around command and query separation. It keeps request dispatching explicit, testable, and easy to reason about inside web apps, workers, and modular backends.

Overview

What Middleman is for

Middleman sits between your transport layer and your application logic. A controller, minimal API endpoint, worker, or service creates a request, sends it through the mediator, and the correct handler executes the use case. That keeps orchestration code small and application logic focused.

For teams using CQRS as a practical boundary rather than a buzzword, Middleman gives you the structure without forcing a heavyweight stack.

Why Middleman

Keep application flow obvious

Use Middleman when:

you want request and handler boundaries, but you do not want your application architecture to revolve around the mediator library itself.

  • Commands express intent for state changes.
  • Queries express read operations and return dedicated result models.
  • Handlers stay close to the business use case they implement.
  • HTTP endpoints become thin dispatchers instead of service orchestrators.

Quick Start

Define a request, add a handler, send it

Basic example 
public sealed record GetOrderById(Guid Id);

public sealed class GetOrderByIdHandler
{
    public async Task<OrderDto> Handle(GetOrderById query, CancellationToken cancellationToken)
    {
        // Load and map your entity here.
        return await Task.FromResult(new OrderDto(query.Id, "Processing"));
    }
}

public sealed record OrderDto(Guid Id, string Status);

var order = await middleman.Send(new GetOrderById(orderId));

The exact interface names depend on the package version, but the core model remains the same: define a message type, implement the corresponding handler, and dispatch from the edge of the application.

CQRS Model

Separate reads from writes

Commands

Commands change state. They should describe intent clearly and keep the write side cohesive. 

public sealed record CreateInvoice(Guid CustomerId, decimal Amount);

Queries

Queries return data and should avoid write-side side effects. 

public sealed record GetInvoice(Guid InvoiceId);

A simple rule helps: if the request changes system state, treat it as a command. If it only reads data, treat it as a query. Middleman gives both patterns a consistent dispatch mechanism.

Handlers

One use case, one handler

  • Keep handlers focused on one request type.
  • Inject only the dependencies required by that specific use case.
  • Return transport-neutral result objects whenever possible.
  • Leave HTTP concerns and serialization at the application edge.
Practical guidance:

if a handler becomes large, the problem is usually the use case boundary, not the mediator. Split the request or extract domain logic.

ASP.NET Core

Thin endpoints, explicit dispatch

Minimal API 
app.MapGet("/customers/{id:guid}", async (
    Guid id,
    IMiddleman middleman,
    CancellationToken cancellationToken) =>
{
    var customer = await middleman.Send(new GetCustomer(id), cancellationToken);
    return customer is null ? Results.NotFound() : Results.Ok(customer);
});

This pattern keeps routing and HTTP details in the endpoint while business behavior stays inside request handlers. It scales well as the codebase grows.

Testing

Test handlers directly

Middleman encourages testing at the request-handler boundary. That gives you focused unit tests without standing up the full web stack for every case.

xUnit sketch 
[Fact]
public async Task Returns_order_when_it_exists()
{
    var handler = new GetOrderByIdHandler();

    var result = await handler.Handle(new GetOrderById(Guid.NewGuid()), CancellationToken.None);

    Assert.Equal("Processing", result.Status);
}

FAQ

Common questions

Is Middleman a full framework?

No. It is a focused mediator library intended to support application boundaries, not replace your architecture.

Does this force full CQRS everywhere?

No. You can adopt commands and queries where they help and keep simpler flows simple.

Should every service call become a request?

No. Use mediator boundaries for application use cases. Keep local private logic as plain methods where that is clearer.
